## 0.3 Changelog (v2.2 → v2.3)
Driven by directly comparing a generated article against a real published Medium article, side by side:

- **Images embedded in the HTML, not just sent as Telegram photos**: the gap was concrete — the banner/illustration images existed (generated via Pollinations, §0.2) but never actually reached the file the user copies from. `app/agent/tools/html_render.py` now embeds them as base64 `<img>` tags directly in `article.html`: the banner right after the title, illustrations swapped in for their placeholder text. `deliver` regenerates the images at delivery time rather than reusing the review-step ones specifically to avoid persisting binary blobs in the LangGraph checkpoint (SQLite) — free regeneration was the simpler trade against that.
- **Illustration-placeholder paragraph bug fixed**: `strip_image_markers()` now forces blank lines around its placeholder text unconditionally. Previously, a marker with no blank line before the following sentence rendered as one merged `<p>` instead of two separate paragraphs — visible in the same side-by-side comparison.
- **New tool `medium_search`**: searches existing *published* Medium articles on the topic (via Tavily's `include_domains=["medium.com"]`, tested live against the real article used for comparison and it correctly surfaced it). Feeds two things: avoiding pure duplication of what's already out there, and calibrating the writing bar against real published work. No DuckDuckGo fallback -- tested live and both the `site:` operator and plain domain-name queries returned empty/unreliable results, so the tool says so explicitly rather than degrading silently.
- **Writing-quality guidance added** to `WRITE_SYSTEM_PROMPT`: explicit anti-"AI-generated-sounding" instructions (vary sentence/paragraph rhythm, avoid transition-word padding and cliché words, take a position instead of a flat both-sides summary) plus an instruction to match/exceed whatever `medium_search` surfaces as the best existing coverage.

## 0.2 Changelog (v2.1 → v2.2)
Driven by feedback from the first live test runs against real Telegram/Gemini traffic:

- **Two Gemini tiers**: `research` stays on `gemini-3.5-flash-lite` (many tool-calling round trips), but `write` moved to `gemini-3.5-flash` — the single call that produces the actual article, where prose quality earns its higher cost. New `GEMINI_WRITE_MODEL` env var.
- **Deeper research**: the prompt now requires ≥5 tool calls across ≥4 tools (was "at least three tools", unspecified count) — early drafts read as shallow with the looser requirement.
- **Live progress in Telegram**: `research` streams its own steps (`_research_agent.astream(...)`, not `.ainvoke()`) and reports each tool call through an `on_progress` callback threaded via `config["configurable"]`, which the bot uses to live-edit a single status message. Previously the bot went silent for the whole research phase.
- **Full draft before approval**: the review step now sends the complete draft as a file with the Approve/Revise buttons attached, not a message truncated at ~3500 characters — a truncated draft is a bad basis for an approve/revise decision.
- **Generated images**: every article gets a banner/cover image; the writer can flag up to 2 spots for illustrations via a `[IMAGE: description]` marker (extracted and stripped in `write_node`, never reaches the delivered article). Generated via **Pollinations.ai** (free, no API key) — an earlier version used Gemini's own image model (`gemini-2.5-flash-image`), which worked but cost $0.039/image; switching cut per-article cost roughly two-thirds. A Mermaid-diagram-based approach was tried and discarded first (looked dated per user feedback) before landing on real generated images.
- **No References section**: sources are tracked separately (state/DB/archive), not appended to the article body anymore.
- **HTML delivery alongside markdown**: `deliver` now sends both `article.md` and `article.html`. This exists because pasting raw markdown text into Medium pastes literal `#`/`**` characters — Medium's paste handler only preserves formatting from real rich-text (HTML) clipboard data, which a *browser* produces when you copy selected rendered text, but Telegram's own copy never does. The user opens the `.html` file in a browser and copies from there instead.
- **`/write` recovery in `on_text`**: some Telegram clients don't tag a pasted `/write ...` message with a bot-command entity, so it fell through to the plain-text handler and got an unhelpful "I don't understand" reply. `on_text` now recognizes and dispatches text starting with `/write` explicitly.
- **Python 3.11+ is a hard requirement**, not a suggestion: `interrupt()` raises on 3.10 when the calling node runs inside an async graph invocation (`ainvoke`, which the bot always uses) — see §3.2. The Dockerfile already targeted `python:3.12-slim`, so only local dev venvs were ever at risk; caught by actually running the app on this machine's default Python 3.10.
- Removed "Image generation for articles" from §2.2 Non-Goals — it's now in scope (see above).

## 0.1 Changelog (v2.0 → v2.1)
Built v2.0 and hit a real-world blocker: Medium has removed self-serve API
integration tokens from account settings (confirmed against a live account —
the "Integration tokens" section under Settings → Security and apps no
longer exists for new integrations). The `publish` node and `MEDIUM_*` env
vars from v2.0 assumed that API was available. v2.1 reflects what actually
shipped:

- **`publish` → `deliver`**: the terminal node no longer calls Medium's API.
  It computes suggested tags; the bot layer sends the finished article to
  Telegram as a `.md` file for the user to paste into Medium's editor
  themselves and publish manually.
- **New command `/published <id> <url>`**: closes the loop — the user
  confirms the manual publish, which records the real Medium URL and (this
  matters) is what triggers `mark_published()`, the same hook that
  populates the `search_past_articles` FTS5 archive from §3.4/§9. Without
  this confirmation step, the archive would never get populated at all,
  since there's no automatic signal anymore that an article actually went
  live.
- **Medium credentials removed entirely**: no `MEDIUM_INTEGRATION_TOKEN`,
  no encrypted per-user token column, no `/connect` flow — there's nothing
  to authenticate, so §4's `users` table and §6's Fernet-encryption row are
  gone rather than deferred.
- If Medium (or a successor workflow) ever exposes a real publish API
  again, only `deliver` needs to change — the graph shape and everything
  upstream of it is unaffected.

## 0. Changelog (v1.0 → v2.0)
v1.0 was designed as a multi-tenant SaaS product. This system is a **single-user, personal daily-publishing bot** driven from Telegram, so v2.0 right-sizes the design:

- **Infra collapsed**: dropped Postgres, Redis, Vault, mTLS, JWT gateway, nginx, 3x/2x replicas, Prometheus/Grafana. One process, one SQLite file.
- **State management**: replaced the custom Redis session schema + `agent_sessions` table with **LangGraph's built-in checkpointer** (`SqliteSaver`), which natively persists graph state per `thread_id` — no bespoke state machine code needed.
- **Human-in-the-loop**: replaced the `REVIEW`/`APPROVED` custom states with LangGraph's native `interrupt()` / `Command(resume=...)` pattern.
- **New tool**: added a **Wikipedia lookup tool** to the Research node for grounded background facts (answers the "LLM wiki" question — see §3.4).
- **Model**: switched target model to Gemini's lite tier (see §5.2 for the exact-ID caveat).
- **No inbound network surface**: Telegram bot uses long-polling, not a webhook, so there's no exposed HTTP port, no nginx, no JWT gateway needed at all.
- **Testing/rollout**: trimmed to match single-user scope (no load testing, no Selenium E2E, no blue-green).
- Enterprise features from v1.0 (multi-tenant DB, Vault, Prometheus/Grafana, replicas) are preserved as a **Future Enhancements** section (§9) in case this ever needs to scale to many users.

## 1. Overview
### 1.1 Executive Summary
An agentic system that automates researching and writing one technical article per day, triggered by a topic message from the owner over Telegram, and hands the finished article back for the owner to publish to Medium themselves. Built on **LangGraph** for orchestration, **Gemini** as the core LLM, with arXiv, GitHub, Wikipedia, web search, page scraping, and a self-archive of past articles as research tools. Runs as a single Docker container on an Oracle VM.

### 1.2 Problem Statement
Content creators face significant time investment in:
- Researching topics across multiple sources
- Synthesizing information into coherent articles
- Formatting for Medium
- Managing the end-to-end content pipeline

### 1.3 Proposed Solution
An autonomous AI agent accessible via Telegram that:
1. Accepts a topic request via chat (`/write <topic>`)
2. Researches the topic via its own past articles, arXiv, GitHub, web search, Wikipedia, and page scraping
3. Generates a well-structured article using Gemini
4. Sends the draft back to Telegram for approval/revision
5. On approval, delivers the finished article as a file for the owner to paste into Medium and publish (see §0.1 — no Medium publish API is available)

---

## 2. Goals and Non-Goals
### 2.1 Goals
| Priority | Goal | Success Metric |
| ----- | ----- | ----- |
| P0 | Accept article requests via Telegram | Bot responds to every `/write` within seconds |
| P0 | Research topic from web + Wikipedia | Minimum 3–5 sources per article |
| P0 | Generate coherent, well-structured articles using Gemini | Human-judged readable on first draft ≥ 80% of the time |
| P0 | Deliver a publish-ready article on approval | Article file arrives in Telegram within seconds of Approve |
| P1 | Human-in-the-loop review before publishing | Approve/revise via Telegram works reliably |
| P1 | Support multiple article formats (tutorial, opinion, technical) | 3+ formats supported |
| P2 | Track basic article history | Queryable via `/status` |

### 2.2 Non-Goals
- Multi-user / multi-tenant support (single owner only — see §9 for future scaling)
- Real-time collaborative editing
- Multi-platform publishing (LinkedIn, Dev.to, etc.)
- Monetization or paywall management
- Automated SEO optimization
- Multi-language article generation
- Semantic (embeddings/vector-store) recall over past articles — implemented as keyword search (§3.4, §9) instead, which is sufficient at this scale

## 3. Architecture
### 3.1 High-Level Architecture
Single container, no exposed ports (Telegram long-polling, all other calls are outbound), SQLite for both LangGraph checkpoints and article records.

```
┌───────────────────────────────────────────────────────────────┐
│                    Oracle VM (Docker Host)                     │
│  ┌────────────────────────────────────────────────────────┐   │
│  │              article-agent container                    │   │
│  │                                                          │   │
│  │  ┌────────────────────┐      ┌────────────────────────┐│   │
│  │  │ python-telegram-bot │◄────►│   LangGraph App         ││   │
│  │  │  (long polling,      │      │  (invoked in-process,  ││   │
│  │  │   no inbound port)   │      │   see §3.2)            ││   │
│  │  └──────────┬───────────┘      └────────────┬───────────┘│   │
│  │             │                                │             │   │
│  │             ▼                                ▼             │   │
│  │      ┌─────────────────────────────────────────────┐      │   │
│  │      │              SQLite (one file, volume)        │      │   │
│  │      │  - LangGraph checkpoints (thread = user)       │      │   │
│  │      │  - articles table (see §4)                     │      │   │
│  │      └─────────────────────────────────────────────┘      │   │
│  └────────────────────────────────────────────────────────┘   │
└───────────────────────────────────────────────────────────────┘
        │outbound            │outbound
        ▼                    ▼
 ┌─────────────┐     ┌──────────────┐
 │ Telegram API │     │  Gemini API  │
 └─────────────┘     └──────────────┘
   (arXiv/GitHub/Wikipedia/web-search/scrape targets are also outbound calls;
    Medium is not called at all — see §0.1, the user publishes manually)
```

### 3.2 LangGraph State Machine
```
        ┌─────────┐
        │  START  │
        └────┬────┘
             ▼
       ┌───────────┐   retry (no/weak sources)
       │  RESEARCH │◄──────────────┐
       └─────┬─────┘               │
             ▼                     │
        ┌─────────┐                │
        │  WRITE  │────────────────┘
        └────┬────┘
             ▼
     ┌─────────────────┐   interrupt() — waits for
     │  REVIEW (human)  │   Telegram /approve or /revise
     └────┬────────┬────┘
   revise │        │ approve
          ▼        ▼
      (back to  ┌─────────┐
       WRITE    │ DELIVER │  -- sends article file to Telegram, no API call
       w/ feedback)└──┬────┘
                      ▼
                 ┌──────────┐
                 │ COMPLETE │
                 └──────────┘
```
- **Checkpointer**: `SqliteSaver` keyed on `thread_id = telegram_user_id`. This alone replaces v1.0's custom Redis session schema and `agent_sessions` table — LangGraph persists the full graph state (messages, sources, draft, feedback) automatically between turns.
- **Human-in-the-loop**: the `REVIEW` node calls `interrupt()`, which pauses the graph and returns control to the Telegram handler. The bot sends the draft + inline Approve/Revise buttons; the callback resumes the graph with `Command(resume=...)`.
- **Retry**: `RESEARCH` self-loops once if fewer than 3 usable sources were found, then surfaces a "couldn't find enough sources" message to the user instead of looping forever.
- **`DELIVER` is not `PUBLISH`**: as of v2.1 (§0.1) there's no Medium API to call here, so this node is graph-terminal, not integration-terminal — the actual publish happens outside the graph, and `/published` (§5.1) is a separate, later confirmation.

### 3.3 Node Definitions
| Node | Responsibility | Tools Used |
| ----- | ----- | ----- |
| **research** | Gathers background info on the topic (ReAct tool-calling loop, `langgraph.prebuilt.create_react_agent`) | `search_past_articles`, `medium_search`, `web_search`, `arxiv_search`, `wikipedia_lookup`, `scrape_url`, `github_search` |
| **write** | Drafts the article from research notes (and prior feedback, if revising); syntax-checks its own code blocks | Gemini, `validate_python_blocks` |
| **review** | Interrupts graph (`langgraph.types.interrupt`), waits on user approve/revise via Telegram | — (human-in-the-loop) |
| **deliver** | Computes suggested tags; graph-terminal. The bot layer (not this node) sends the article file to Telegram — see §0.1 | — (no Medium API available) |

### 3.4 Tools
Built and implemented — see `app/agent/tools/`.

| Tool | Purpose | Notes |
| ----- | ----- | ----- |
| `search_past_articles` | **Implements the "LLM wiki" ask.** Keyword search over this blog's own previously *published* articles | SQLite FTS5 index, populated in `mark_published()`. Checked first in the research prompt so new articles build on/diverge from prior coverage instead of repeating it. Keyword, not semantic — see the note below. |
| `medium_search` | Searches existing *published* Medium articles on the topic — the wider ecosystem, not just this blog | Tavily `include_domains=["medium.com"]`. Requires `TAVILY_API_KEY`; no DuckDuckGo fallback (tested live, unreliable for domain-filtered queries). §0.3. |
| `arxiv_search` | Paper-backed grounding for research-heavy claims (new architectures, training techniques, algorithms) | Wraps the `arxiv` PyPI package directly, not a langchain-community wrapper. |
| `github_search` | Verifies a library/tool/technique referenced in the article actually exists and is maintained; finds a canonical repo to link | GitHub REST search API; works unauthenticated, `GITHUB_TOKEN` raises the rate limit. |
| `wikipedia_lookup` | Grounded background/definitional facts | Wraps the `wikipedia` PyPI package directly. Good for terminology and history; won't have anything recent, so pair with `web_search`. |
| `web_search` | General/recent web search for the topic | Tavily if `TAVILY_API_KEY` is set, DuckDuckGo otherwise (no key required to run). |
| `scrape_url` | Extract clean article text from a URL found by search | `trafilatura`. |
| `validate_python_blocks` | Not an LLM-facing tool — a plain `ast.parse` syntax gate the `write` node runs on its own output | Warnings surface in the Telegram review card rather than blocking; catches syntax errors, not runtime correctness. |

**On "LLM wiki"**: implemented as `search_past_articles` above — a keyword-search (SQLite FTS5) archive of this blog's own published output, not a general Wikipedia-alternative and not a vector store. A *semantic* version (embeddings + a vector DB, so a query like "RAG evaluation" also surfaces an article titled "measuring retrieval quality") was considered and deliberately deferred: LangGraph does ship a cross-thread `Store` abstraction built for exactly this, but its only persistent backend requires Postgres, which would reintroduce the infra this design cut in v2.0. At roughly 365 articles/year, keyword search is enough to catch duplicate topics; upgrading this one tool to embeddings later is a contained change, not a rewrite. See §9.

## 4. Data Model
Everything lives in one SQLite file (`data/agent.db`), mounted as a Docker volume.

```sql
-- Articles: one row per requested article
CREATE TABLE articles (
    id TEXT PRIMARY KEY,                 -- uuid
    telegram_user_id INTEGER NOT NULL,
    topic TEXT NOT NULL,
    article_type TEXT DEFAULT 'general', -- tutorial|opinion|technical|news
    status TEXT DEFAULT 'researching',   -- researching|drafted|awaiting_review|revising|delivered|published|failed
    title TEXT,
    content TEXT,
    sources TEXT,                        -- JSON array [{url, title, snippet}]
    medium_url TEXT,                     -- set by /published, not by the graph (§0.1)
    medium_post_id TEXT,                 -- always NULL now -- no API response to source it from
    created_at TEXT DEFAULT CURRENT_TIMESTAMP,
    published_at TEXT                    -- set by /published, i.e. when the user confirms, not when `deliver` runs
);

-- LangGraph's SqliteSaver manages its own checkpoint tables automatically —
-- no custom session/state tables needed (this replaces v1.0's agent_sessions table).

-- No `users` table: v2.0 planned one for an encrypted Medium token, but v2.1
-- (§0.1) has no Medium credential to store at all, so it's gone rather than
-- deferred.
```

## 5. API / Integration Design

### 5.1 Telegram Bot Commands
| Command | Description | Parameters |
| ----- | ----- | ----- |
| `/start` | Register/greet | None |
| `/write` | Start a new article | `<topic> [\| tutorial\|opinion\|technical\|news]` |
| `/status` | Check current or past article status | `[article_id or prefix]` |
| `/published` | Confirm a delivered article was manually published on Medium; records the URL and adds it to the `search_past_articles` archive (§0.1) | `<article_id or prefix> <medium_url>` |

Inline buttons (Approve / Revise) on the draft message are the primary UX for the review step; `/write`, `/status`, and `/published` are typed commands. There is deliberately no `/connect` — no Medium credential exists to connect (§0.1).

### 5.2 Gemini Integration
```python
import os
from langchain_google_genai import ChatGoogleGenerativeAI

# Read from env, don't hardcode: Gemini model IDs change across release
# cycles. "gemini-3.5-lite" (no "flash") 404s -- confirmed live against the
# ListModels endpoint -- Gemini's lite tier is always named "flash-lite".
GEMINI_MODEL = os.environ.get("GEMINI_MODEL", "gemini-3.5-flash-lite")

llm = ChatGoogleGenerativeAI(
    model=GEMINI_MODEL,
    google_api_key=os.environ["GEMINI_API_KEY"],  # must be passed explicitly --
    # pydantic-settings loading .env into our own Settings object does NOT
    # export it to os.environ, and this client reads os.environ directly
    # if the key isn't passed as a constructor arg. Caught by running the
    # app for real; see app/agent/nodes/research.py and write.py.
    temperature=0.4,
)
```
Keeping the model name in an env var means a wrong/renamed ID is a one-line config fix, not a code change.

### 5.3 Medium Delivery (not an API integration — see §0.1)
Medium's `POST /users/{userId}/posts` endpoint from v2.0 is not reachable via a self-serve token anymore, so there is no request payload to define here. Instead, `deliver` (§3.3) computes tags and the bot layer sends Telegram a `.md` document:

```python
# app/bot/telegram_bot.py — illustrative, see the file for the real version
filename = f"{slugify(title)}.md"
document = InputFile(io.BytesIO(content.encode("utf-8")), filename=filename)
caption = (
    f"Ready to publish: {title}\n\nSuggested tags: {', '.join(tags)}\n\n"
    "Paste into Medium's editor, add the tags, hit Publish, then:\n"
    f"/published {article_id[:8]} <medium url>"
)
await bot.send_document(chat_id, document=document, caption=caption)
```
`/published` (§5.1) is what turns the user's manual publish into a state-machine event — it's the only place `mark_published()` (§0.1, §9) is called.

## 6. Security Considerations
Right-sized for a single-user process with no inbound network surface (Telegram long-polling means there's nothing to open a port for):

| Concern | Approach |
| ----- | ----- |
| Bot token / API keys | Environment variables only, never committed; loaded via `.env` + Docker Compose `environment:` |
| Scraped content → prompt injection | Strip HTML/scripts before passing scraped text into the LLM context; treat scraped text as untrusted data, not instructions |
| Scraping etiquette | Respect `robots.txt`, reasonable per-request delay, no scraping domains that disallow it |
| Outbound-only network | No nginx, no JWT gateway, no mTLS — there is nothing listening for inbound traffic to secure |

Vault, RBAC, and audit-log infrastructure from v1.0 are overkill for one user and are deferred to §9.

## 7. Testing Strategy
| Category | Scope | Tools |
| ----- | ----- | ----- |
| Unit tests | Each tool (`search_past_articles`, `web_search`, `arxiv_search`, `wikipedia_lookup`, `scrape_url`, `github_search`, `validate_python_blocks`), the `deliver` node's tag logic, and the DB layer (FTS5 archive, prefix lookup) | `pytest`, `unittest.mock` |
| Graph integration test | Run research/write/review/deliver wiring against a stub write node end-to-end, including an interrupt/resume cycle | `pytest` + LangGraph's in-memory checkpointer |
| Manual E2E checklist | Real `/write` → real draft → approve → confirm the article file arrives → paste into Medium → `/published` → confirm it's tracked, run once before each deploy | manual |

Load testing, Selenium E2E, and OWASP scanning from v1.0 are dropped — there's one user and no exposed HTTP endpoint to attack-surface-test.

## 8. Rollout Plan
| Phase | Duration | Activities | Success Criteria |
| ----- | ----- | ----- | ----- |
| **Phase 1: Core graph** | Week 1 | Build LangGraph app (research/write/review/deliver nodes), test locally | Full graph runs end-to-end against mocks |
| **Phase 2: Real integrations** | Week 2 | Wire up real Gemini, Telegram bot, `/published` command; SQLite checkpointing | One real article delivered and manually published end-to-end |
| **Phase 3: Deploy & trial** | Week 3 | Docker Compose deploy to Oracle VM, run daily for a trial week | 5+ consecutive daily articles delivered and published successfully |

### Rollback
Single container, so rollback is just: `docker compose down && docker compose up -d --build <previous tag>`. No blue-green needed at this scale.

### Monitoring
Structured JSON logs to stdout (captured by `docker logs` / journald) are sufficient at this scale — log each node transition, tool call, and delivery/`/published` event. Prometheus/Grafana are deferred to §9 rather than run for a single daily job.

## 9. Future Enhancements (deferred, not in scope for v1)
- **Semantic research memory**: upgrade `search_past_articles` (§3.4) from SQLite FTS5 keyword search to embeddings + a vector store (e.g. Chroma), if keyword recall ever proves insufficient for surfacing related prior coverage.
- **Multi-user support**: reintroduce a proper Postgres schema, per-user isolation, and the JWT-gated API layer from v1.0 if this ever moves beyond a personal tool.
- **Scheduled/autonomous topic selection**: if no `/write` arrives by a set time, have the agent propose a topic itself (e.g. from trending sources) instead of staying idle.
- **Automated/multi-platform publishing**: revisit if Medium restores API access, or add platforms whose APIs are still self-serve (e.g. Dev.to) as additional deliver-style nodes — each would need its own manual-vs-API decision the way `deliver` did for Medium (§0.1).
- **Observability stack**: Prometheus/Grafana if this needs to be monitored by more than one person, or if reliability becomes business-critical.
- **Vault/mTLS**: only worth it once there's more than one deployment environment or more than one operator with access.
